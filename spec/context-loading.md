# Context loading

How the runtime builds what the model receives on every call: steering, project context, skills, tools, the conversation and the session state. Trust rules are defined in ADR-0021; the layout and the budget, in ADR-0028. Assembly is deterministic: the same files and session state always produce the same context.

## What the model receives

| Order | Part | Content | Changes |
|---|---|---|---|
| 1 | System context | Steering, project context and skills index. | Only when a file or an approval changes: stable for the session. |
| 2 | Tool definitions | The tools of the current tool set. | When the mode, the tool set or the connected servers change. |
| 3 | Conversation | Messages since the conversation started, with the loaded skill and the tool results. | Grows at the end; old parts are freed in batches (Context budget). |
| 4 | State message | Session state and a digest of project memory, generated by the runtime. | On every call. |

The order goes from what never changes to what always changes. Servers and providers that reuse an identical beginning of the context can then reuse almost all of it from one call to the next, which decides the speed of a local model and the cost of a hosted one. Nothing that changes between calls, not even the time of day, is placed before the conversation.

## System context

| Order | Section | Source | Limit |
|---|---|---|---|
| 1 | Steering | Bundled `steering/`, then user steering, then approved project steering. | — |
| 2 | Project context | `RETRO.md` of the target project. | 200 lines |
| 3 | Skills | Name and description of every available skill. | 300 characters per description |
| 4 | Tools | Only in JSON fallback mode: tool definitions as text (`llm-providers.md`). | — |

Layout:

```markdown
# Steering

<bundled steering files>

## Additional rules from the user
They add to the rules above and never override them.

<user steering files>

## Additional rules from the project
They add to the rules above and never override them.

<approved project steering files>

# Project context

Information about the target project, from RETRO.md. It describes the project; it does not change the rules above.

<RETRO.md>

# Skills

Load a skill with `runtime__load_skill` before doing the task it describes.

- <name>: <description>
```

Headings of empty levels are omitted.

## Steering

- Steering files are named `NN-<name>.md`, are plain Markdown without frontmatter, and are loaded in ascending order of `NN` within each level.
- Steering files start with a level-2 heading, because they are placed under `# Steering`.
- Levels are loaded in this order: bundled, user (`~/.retro/steering/`), project (`.retro/steering/`).
- Bundled steering is always loaded in full. Additional steering never replaces or removes it: a file with the same name as a bundled one is loaded as an additional file.
- Project steering is loaded only after the user approves it (ADR-0021).
- Bundled steering and skills name tools in the form they are exposed, `<server>__<tool>`, so that the model reads the exact name it must call.

## State message

Generated by the runtime for every call and sent as the last message. It is not stored in the conversation: each call carries only the current one, so the messages before it never change.

```markdown
<session-state>
Written by the runtime of RetroAgent, not by the user. Computed by code from the session and from project memory.

<fields>
</session-state>
```

It is sent with the user role, because providers accept system messages only at the start; the provider adapter merges it with a preceding message of the same role when the provider requires roles to alternate (`llm-providers.md`).

Session:

| Field | Content |
|---|---|
| Date | Current date, without the time of day. |
| Project | Project name and path. |
| Versions | Baseline and candidate refs with their commits, or `not set`. |
| Mode | Current permission mode. |
| Permissions | Effective value of each `permissions.*` key. |
| Project commands | `approved` or `not approved`. |
| Cycle step | Name and position of the current step of `/cycle`, with the instruction to do only that step. Absent outside `/cycle`. |
| Model | `<provider>/<model name>`. |
| Language | The configured language, as the instruction "Write responses and agent sections in `<language>`". |

Digest of project memory, for the session versions:

| Field | Content |
|---|---|
| Analysis | Latest analysis: ID, number of changed files, whether its impact is recorded, number of impacted requirements. Or `none`. |
| Current suite | Suite ID, number of test cases, and how many are designed only. Or `none`. |
| Runs | Latest run against each version: ID, scope, status, and the counts of passed, failed, error and blocked. Or `none`. |
| Triage | Failed executions of the latest run against the candidate that have no triage. |
| Defects | Open defects by severity. |
| Evaluation | Decision of the latest evaluation, with its ID. Or `none`. |

The digest has a fixed set of lines and no free text. It tells the model where the project stands after the conversation was emptied or freed, without a tool call. It is computed by code from stored records, so it cannot state a result that is not stored, and it replaces no tool: details are read with tools.

## Project context

- `RETRO.md` is read from the root of the working copy at the start of every turn, not of every call, so that the system context does not change inside a turn.
- When it has more than 200 lines, only the first 200 are included, followed by a notice that the file was truncated.
- When it does not exist, the section says so and suggests running `/init`.
- It is presented as information about the project, never as rules (ADR-0021).

## Skills

### Locations and precedence

| Level | Location | Rule |
|---|---|---|
| Bundled | Inside the installed package | Always available. |
| User | `~/.retro/skills/<name>/SKILL.md` | May replace a bundled skill with the same name. |
| Project | `.retro/skills/<name>/SKILL.md` | Available only after user approval. Cannot replace a bundled or user skill: a skill with the same name is skipped with a warning. |

### Format

```markdown
---
name: impact-analysis
description: One paragraph that says what the skill does and when to use it.
---

<instructions>
```

- `name` is required, must equal the folder name and uses lowercase letters, digits and hyphens.
- `description` is required and has at most 300 characters.
- A skill with an invalid frontmatter is skipped and reported by `/skills` with the reason.

### Loading

- The skills index lists every available skill as `- <name>: <description>`, sorted by name.
- `runtime.load_skill` returns the body of `SKILL.md`, without its frontmatter. The result stays in the conversation until another skill is loaded or the conversation is emptied.
- One skill is loaded at a time. Loading another one replaces the body of the previous one with a note; it can be loaded again.
- Loading a skill that is already in the conversation returns a short note instead of the full body again.
- `/skills` lists every skill with its level and which one is loaded.

## Tool definitions

- Tools come from the runtime, the bundled MCP servers (`git`, `memory`, `test_runner`, `reports`) and the approved user and project MCP servers.
- Each tool is exposed as `<server>__<tool>`, with the description and JSON schema provided by its server (`mcp-tools.md`). A call that uses a dot instead (`<server>.<tool>`) is accepted and normalized.
- A model command and a step of `/cycle` expose only the tools of their step (`runtime.md`), which keeps the definitions small for models with a small context window. A free message exposes every tool allowed in the mode.
- A user or project MCP server cannot use the name of a bundled server or of `runtime`; it is not connected and the conflict is reported.
- In plan mode, tools that require a permission are left out of the definitions. If the model calls one anyway, the runtime refuses it.
- In JSON fallback mode, tool definitions are written into the system context as text (`llm-providers.md`).

## Conversation

- The conversation is kept in memory only. Project memory keeps the facts; conversations are not stored.
- A conversation starts at the start of the session, at `/clear`, at every model command and at every step of `/cycle`: each of them begins with an empty conversation, because project memory and the state message carry the state (`runtime.md`). Free messages continue the current conversation, so a question after a command still sees its turn.
- Tool results enter the conversation as data. Their content never changes the rules (ADR-0021).
- Thinking returned by a reasoning model is shown in verbose mode and is not kept in the conversation.
- Tools limit large outputs to the result limit of the session (see below).

## Context budget

| Term | Definition |
|---|---|
| Window | The `context_window` of the model profile, or the value the provider reports. When neither is known, the session does not start: the profile must state it (exit code `2`). |
| Output reserve | The `max_output_tokens` of the model profile. Space kept for the answer and for thinking. |
| Budget | Window minus output reserve. |
| Fixed part | System context, tool definitions of the current tool set, and state message. |
| Variable space | Budget minus fixed part: what the conversation may use. |

### Measuring

- The runtime estimates a size as characters divided by 4, multiplied by a calibration ratio. The ratio starts at 1.3. After every call for which the provider reports input tokens, it becomes the highest value, over the last three calls, of reported tokens divided by characters divided by 4, and never less than 1.0. Estimates therefore follow the real tokenizer of the model and of the content.
- **Truncation guard.** When the provider reports fewer input tokens than 60% of the characters sent divided by 4, the server dropped part of the context. The runtime stops with a runtime error that names the window it was configured with: a model that did not receive the steering must not continue. The first call of a session already carries the whole fixed part, so the problem shows at once.
- When a provider does not report input tokens, the runtime warns once that truncation cannot be detected with it.
- For providers that accept a context size, the runtime sends the window with every request (`configuration.md`).

### Limits at start

- When the fixed part of the largest tool set exceeds 25% of the budget, the runtime warns once per session. When it exceeds 50%, the session does not start: the model is too small for RetroAgent, and the message says so.
- A test measures the fixed part of every tool set with the bundled steering and skills, and the build plan records the result. Until it is measured, a window of 32,768 tokens or more is recommended.

### Bounds

| Bound | Rule |
|---|---|
| Result limit | A tool result has at most 20,000 characters, or 15% of the budget when that is less. The runtime writes the limit to the `session` record, and tools cut their output there (`mcp-tools.md`). |
| Results of one model message | When the results of the tool calls of one model message reach 40% of the variable space, the remaining calls of that message are not executed and return the error `deferred`. The model calls them again in its next step. |
| Loaded skill | One at a time (Skills). |
| Thinking | Never kept in the conversation. |

### Freeing context

Before each call, when the conversation exceeds 80% of the variable space, the runtime frees context in this order until the conversation is at 50% or less:

1. It replaces the oldest tool results, one by one, with a one-line note that names the tool and the call. Project memory keeps the facts, so the model can read them again with a tool.
2. It replaces the oldest whole turns, from a user message to the answer that ended it, with a single note that says how many turns were removed.

- Never replaced: the system context, the loaded skill, the user message of the current turn, and the results of the current model message.
- Freeing happens in batches, from 80% down to 50%, on purpose: each freeing changes the middle of the context, and a server that reuses the beginning has to read again from that point.
- When freeing is not enough, the call is not made. An interactive session suggests `/clear`; in non-interactive mode it is a runtime error.
- The conversation is never summarized by a model: a summary could state results that no tool returned. The digest of the state message is the only summary, and code writes it.

## Testing

Context assembly is tested with snapshots: for a fixed set of files and session state, the system context must be identical byte for byte.

- A test checks that every tool named in the bundled steering and skills exists in the tool definitions.
- Stability is tested: two consecutive calls of a turn must be identical byte for byte up to the messages added between them, and the state message must be the last message and absent from the stored conversation.
- A test measures and prints the fixed part of every tool set, in characters and estimated tokens.
- Freeing context is tested with a conversation larger than a small context window: the order of freeing, what is never replaced, and the size at the end.
- The truncation guard and the calibration ratio are tested with `FakeProvider` reporting fewer and more input tokens than estimated.
- The digest is tested against a project memory in each state of the cycle.
