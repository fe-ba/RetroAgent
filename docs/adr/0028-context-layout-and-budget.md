# ADR-0028: Context layout and budget

- **Status:** Accepted
- **Date:** 2026-11-15

## Context

ADR-0027 introduced a context budget: a known window, an estimate of characters divided by 4, and the replacement of old tool results when the context reached 70% of the window. Measuring the bundled files and testing two local models showed where that design fails:

- The steering alone is about 2,700 tokens, and the tool definitions are estimated at 5,000 to 7,000. With a window of 16,384 tokens the fixed part exceeds half of it: the session would not start, and the rule "free down to 50% of the window" could never be met.
- A local server that was not told the context size read 2,050 of 8,070 tokens and returned no error. The rule "send the context size to servers that accept one" does nothing for servers that do not.
- On modest hardware the model read about 30 tokens per second, so reading the fixed part again costs minutes. Servers reuse an identical beginning of the context, but the session block, which changes on every call, was placed before the conversation, and each freeing changed the middle of it.
- Model answers, loaded skills and the results of the current call were never freed, so they could fill the window by themselves, with `/clear` as the only way out.
- After the conversation was emptied or freed, the model had to spend calls to find out where the project stood, or continue from what it remembered.
- Nothing reserved space for the answer, which matters with reasoning models.

## Decision

1. **Order by stability.** System context, then tool definitions, then conversation, then a state message generated by the runtime as the last message of every call. Nothing that changes between calls is placed before the conversation. The state message is never stored in the conversation.
2. **A digest computed by code.** The state message carries the session state and a fixed digest of project memory: analysis, suite, runs, untriaged failures, open defects, evaluation. It is the only summary the model receives, and the model does not write it.
3. **Measure, do not guess.** Estimates are calibrated with the input tokens that providers report. A call for which the provider reports far fewer tokens than were sent stops the session: the truncation guard.
4. **The budget is the window minus an output reserve,** and thresholds apply to the space left for the conversation, not to the whole window.
5. **Everything is bounded.** Tool results by a limit proportional to the budget; the results of one model message by a share of the conversation space; one loaded skill; thinking never kept; whole old turns freed after old tool results.
6. **Every model command starts with an empty conversation,** not only the steps of `/cycle`.
7. **Skills work incrementally:** read one item, record the conclusion, read the next.
8. **Tool descriptions have a maximum length,** and a test measures the fixed part of every tool set.

## Alternatives considered

- **Let the model summarize the conversation:** recovers more reasoning than a digest, but a summary can state a result that no tool returned (ADR-0006, ADR-0027).
- **Keep the session state in the system context:** simpler, and common, but any change in it invalidates everything a server had already read.
- **Count tokens with the tokenizer of each model:** exact, but tokenizers differ per model and are not available for every provider; the reported usage is available for most and costs nothing.
- **A small probe call at start to detect truncation:** detects it before the first real call, at the cost of one call per session. The first real call already carries the whole fixed part, so the guard catches it there.
- **Lower the minimum by shrinking the steering:** the steering is what the course evaluates; tool descriptions are bounded instead.

## Consequences

- A model with a window under about 32,768 tokens is expected not to work. The real minimum is known once the tool definitions exist and the test measures them.
- With local models, only the first call after a change of step or after a freeing reads the whole context. With hosted models, the stable beginning can be cached, which lowers the cost of each call.
- The state message is one more thing every provider adapter must place correctly.
- A provider that does not report input tokens gets no truncation guard and no calibration; the runtime says so.
- A model command no longer sees what was said before it. What must survive has to be in project memory, which was already the rule for `/cycle`.
- The digest must stay small and fixed. Adding free text to it would bring back the problem it solves.
